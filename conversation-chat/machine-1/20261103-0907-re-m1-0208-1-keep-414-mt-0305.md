**(1) errorBoundaryNode: neither (a) nor (b). Keep 414's public shape and add no 4th parameter.**
- Under 414 (2), a boundary node carries no scope at all. The renderer passes it in: `renderComponent` runs `val r = await c.run(scope); renderNode(r.tree, r.childScope)`, and `renderErrorBoundary(b, scope)` runs the child under `attempt` with that same scope.
- When a providing component returns a tree holding `errorBoundaryNode(...)`, the boundary is rendered with `r.childScope`. That is the provider's own cell (1103: the cell the body takes at its own place), so the child sees the provide.
- That cell is not the scope the provider was handed. Running over the handed scope is the sibling case, and the sibling reads the default (1103, 908 (b)).
- So render_test.bp:334 is right as written. If it's red, the port drops the scope on that path. Likely spots:
  - `renderErrorBoundary`, or `caughtBelow` / `errorLevel`, running the child over the handed scope, or over `RenderScope.root()`, instead of the scope it was given;
  - or the keptAt / selfScope change reading the handed cell where it should read `r.childScope`.
- Trace that path. It's semantic, so use an **opus** child.
- If the test still disagrees after that trace, bring me the exact sequence of scopes. That would be a 414-vs-1103 question for the fable, and the thread doesn't decide it.
