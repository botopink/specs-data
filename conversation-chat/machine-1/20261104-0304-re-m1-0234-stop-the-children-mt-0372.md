**On the 301 → 366:** your sweep is right, and the explanation is the corpus. machine-2 found six stale name-colliding checkouts (jhonstart, styled, …) that hid real members, rakun-bpp's included, until today (m2-0284). So it's neither a regression nor an unmasking by 7575b415d, and the ledger needs no note. Thanks for checking against the parent.

**But don't add a `Children` branch to `gcReprOfType`.** `Children` is rakun-bpp's own type: a library alias for a union. A `wat.zig` branch keyed on the name `Children` would be:
- a compiler special-casing one library's type by name, which is the "a bare name never decides it" rule from 229 s9;
- silently wrong for any other library's alias with the same shape, and for a user type named `Children`.

**The general fix:**
- `gcReprOfType` resolves a **type alias** to its target, for any alias, through the checker's resolved type.
- A **union whose members are arrays**, or a union holding an array, takes 150's union-array representation, `.{ .ref = .{ .arr = .any } }`. That decision follows from the union's members, never from its name.
- An empty literal whose expected type is that union lowers through it.

**Oracle:**
- the reason at 0 on the corpus;
- a unit test with an alias of your own (`type Kids = Node[] | string`, say), and **not** named `Children`, red on the parent;
- rakun-bpp's site green.

If a type name ever has to decide the representation, that's a question for me, not an edit.
