The fable's verdict is **(A)**, and it needs no new decision. It is the fourth application of one rule:
- 568: the tuple's own GC subtype, no boundary conversion;
- `$box_bool <: $box_i32` (wat.zig:6667);
- 1031 (2): bigint's own box.

In the landing report, cite 568 / 1031 (2).
- **mt-0237 doesn't cover this.** It was B-204's i64 hash on the *linear* path (`allocTagged`). Its principle ("two boxing mechanisms is a trap") argues *for* (A). With (B), `bool[]` would have two representations, and the `ref_cast $arr_i32` read-back in `gcUnbox` (:7905) would trap or need a second copy.
- **547 is the module-`var` row, not array values.** Immutability comes from the reference and 544; (B) would be correct, only expensive. That doesn't change the verdict.

**Design (A):**
- `wat/repr.zig:72` `Elem` gains `.bool`; the exhaustive switches name every site.
- `gcElemOf` (:7194) and `gcElemClassOf` (:7909) map `.bool` to `.bool`.
- `gcBuildTypes` (:7577): `arr_bool` has elem `i32` and `.super = arr_i32`; `$arr_i32` is not final when `arr_bool` exists; `gcTyIndex` declares `arr_i32` first.
- Every helper's `switch (cls)` gets a `.bool` arm that computes as `.i32` with its own type index.
- Printer `gcArrsPrinter` (:11254): a `.bool` arm tested **before** `.i32`, subtype first.
- Equality: `__unk_eq_arr_bool`, and `gcUnkEqRef`'s `.i32` arm with `not_vt = arr_bool`.
- `gcGenericArg` (:27169-27170): drop the `[i` / `[f` / `[s` whitelist, so any array shape without `u` is accepted. Nested arrays already print through `[U` → `__print_arrs`.
- Prelude: if units exchange arrays, `arr_bool` joins `arr_i32` in `wat_prelude.zig:2499` `GcSlot`. Check where `arr_i32` sits first.

**The other two refusals, independent of the choice:**
- **Tuple** (:27176): `gcTupleLit` already boxes a bool as `$box_bool`. Accept `b` and verify. A unit enum goes through `.ebox`, as :27202 does.
  - **`u64` stays refused in this step.** If you hit it, report it as a row: `$box_u64 <: $box_i64` is the future shape.
- **Named word array into `Array<T>`** (:27188): lift "literal only", and use `gcArrBox(vr.ref.arr)` for any named `$arr_i32` / `$arr_f64` / `$arr_bool`. This is where mt-0237's "reuse the boxing path" does apply.

**Risks:**
- A helper hard-coded to answer `$arr_i32` traps on a `bool[]` local's `ref_cast $arr_bool`. Cover it with a cell that runs a `bool[]` through `filter` / `slice` / `concat` / `map` into `Box<T>`.
- The GC `.wat` snapshots that hold bool arrays get re-recorded. No printed answer moves.
- `Color[]` (a unit-enum array) stays refused. That is out of scope.

**Cells (commonJS's answers):**
- `Box(value: [true, false])` → `Box(value: [true, false])`
- `Pair(first: #(true, 1), second: "x")` → same
- `Box(value: [[1, 2], [3]])` → same
- `Box(value: [[true], [false, true]])` → same
- `val xs = [7, 8]; Q(items: xs)` → `Q(items: [7, 8])`
- `Box(value: [true]) == Box(value: [true])` → `true`
- a `bool[]` through `filter` into `Box<T>` → `[true]`

Each is red on the parent and green after, on 4 targets. Front 170 s7's "array of tuples in a type-parameter slot" closes with it. Go, on the opus child.
