Rebased rakunshapea onto current origin/feat (both botopink-lang and rakun), rebuilt nothing (used the main checkout's compiler, already at 90fa96f7a). Re-ran my repros and went further. Good news first, then the new blocker.

**Confirmed fixed, both from mt-0394:**
1. B-147-erlang: an instance method handed as a bare value now works correctly on erlang — `decl(instance, req)` with `decl` captured generically (`fn(self: unknown, req: string) -> string`) runs right, cross-module, self+extra-arg included.
2. The owner-grouped join itself works end to end: a method marker registering `(owner, verb, path, decl)` + a type marker registering `(owner, make)` + a dispatcher resolving the owner's factory and calling `decl(instance, req)` — built this whole thing from scratch and it dispatches correctly on erlang.
3. `compiler.ast` (B-149) can build a type's real `make()` body with DYNAMIC field counts as a literal (not text) — `Call`/`Arg`/`Lambda` nodes looping over `compiler.fields(decl)`, including the `rkEnter`/`rkSingleton` bracket (no local-`val` AST node exists — `compiler.Lambda.body` and `compiler.Fn` have none — so I factored the bracket into one new named helper function, called by name from the tree, instead of inlining three statements). This part works and is exactly decision 842 (1)'s shape.

**The new blocker, not B-235/640(3)/B-147/B-149, found going past where mt-0394 answered:** rakun's real stereotypes resolve injected fields through `rkResolve`/`rkProp`/`rkPropInt`, all three defined in `context.bp`. `compiler.ast`'s `Name` resolves in the decorator's OWN module (decorators.bp), and `decorators.bp` cannot import from `context.bp` — `context.bp` itself imports from `decorators.bp` (confirmed: `grep decorators\. context.bp` hits), so the dependency runs the other way; `config.bp` does too. There is no file-order fix here, it is a real cycle.

I tried the obvious workaround — keep `make()`'s existing text (`addMember`, one-arg form, unchanged, still works today) and build the SEPARATE value handed to `rkRegisterFactory` as a tiny `compiler.ast` tree that calls it by name, `Member(target: Name(owner), member: "make")`, never through `decl`. That type-checks and runs correctly when called directly as another member (`Widget.viaAst()` → right answer, erlang and commonJS both). But the moment the SAME closure is held as a value (`val make = fn() -> decl { return compiler.ast(callMake); }`, handed to `compiler.init` and called later from a different module, exactly 842 (1)'s shape) — it compiles clean and crashes at run time: `crash: undef`, erlang only. Minimal repro: a `component`-style decorator builds `make()` as today's text, then builds a second value via `compiler.ast(Call(callee: Member(target: Name(owner), member: "make"), args: []))`, hands it to `compiler.init`, stores it in a module `var`, and calls it from `main` in a different module. This is a new, distinct defect from B-147 (that one was about `decl` itself as a value; this is a `compiler.ast`-built closure that calls a static method by name as a value) — not filed anywhere I can find under B-147 or B-149's rows.

So the one piece left unbuildable is specifically the make()-with-injected-fields case (every real rakun stereotype: component/service/repository/controller/restController/configuration). A fieldless type's factory (my `Users()`/`Widget()` repros) builds and joins fine both ways. I have not touched any rakun file — worktree stays clean, no commit.

Options as I see them: (a) file this as a new B-147-class row for machine-2 (a `compiler.ast`-built closure calling a static method by name, held as a value, undef on erlang) and wait; (b) break the `decorators.bp`/`context.bp` cycle by moving `rkResolve`+its three dependencies (`rkCatalogueEntry`, `chooseBean`, `rkBeanInvoke`) earlier in the file order — a real, if contained, restructure of context.bp I have not attempted; (c) something else. Which do you want, or should I just start on (b)?
