P3 is reworked to 1026 on its branch (871e4534b, rebased on feat e456bf80c), not landed.

What it does:
- `std@__rt` holds only the core: memory, `__heap_ptr` / `__alloc`, the panic tag, the WASI imports, std-wasm's data and stack, and the 17 helpers that several units share. It exports no `std:` function.
- std-wasm is split into units: `std@number` (36 functions), `std@string` (65), `std@array` (25), `std@bigint` (14), `std@bytes` (5), `std@encoding` (14), `std@hash` (11), `std@heap` (37), `std@io@fs` (31, imports `bp_fs`), `std@io@random` (7). The graph is acyclic; `zig build std-wasm` writes the core plus every unit.
- A program composes the core, then only the units it reaches in dependency order, then its entry.
- The `.wat` leaves moved into their units.
- The data reserve is sized from the entry's data. The 16-page limit and its refusal are gone.

Proof:
- CLI test `wasm_std_unit_per_module.sh` (the cell): hello-world composes core + main only; an io.fs program adds `std@io@fs`; both answer as on erlang.
- 345 wasm snapshots re-recorded; I checked 344 RUN LOG blocks are identical. The one that changed was already red: a core-module run cannot bind `bp_fs`, and now one more preload line comes before the same `unknown import` error.

Sizes of `main.wat`:

| program | before P3 | first P3 | reworked P3 |
|---|---|---|---|
| hello-world | 14 KB | 748 KB | 56 KB |
| float + split string | 121 KB | — | 594 KB |

The float + split program grows because each unit it reaches (`std@string`, `std@number`) is embedded whole as text in the component.

Questions (recommendation first):
1. **Unit names for std-wasm modules that no std `.bp` declares:** the thread chose `std@array`, `std@bigint`, `std@bytes`, `std@heap`, plus `text` → `std@string` and `random` → `std@io@random`.
   (a) keep these names;
   (b) name each after the std `.bp` module that binds it.
2. **Where `$__write_bytes` and the GC print helpers go.** They stay in the entry because they depend on the program's capture state.
   (a) move them in P4, with the type registry;
   (b) leave them per entry.
3. **The size growth for string/number programs:**
   (a) the binary component encoder now (a P3 follow-up before landing): the frame embeds each unit's bytes, so the text grows by about the binary size and wasmtime stops re-parsing unit text;
   (b) prune each embedded unit to what the program reaches (this cuts against "written once", 1026 (2));
   (c) land as is and decide after P8's measurement.

My recommendation: 1(a), 2(a), 3(a). I hold P3 until you answer 3.
