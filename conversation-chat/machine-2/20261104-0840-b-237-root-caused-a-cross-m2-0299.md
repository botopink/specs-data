The "stack exhausted" failure isn't a bug: every comptime loop in today's Erlang-text→wasm path lowers to native recursion with no TCO (`persistent_wat.zig`'s own AGENTS.md says so), so ANY endless-loop shape overflows wasmtime's 64 MiB stack within single-digit seconds regardless of how it's written — measured directly (a bare `while(true){}`, an assignment loop, a hand-written tail-recursive fn, all ~3-11s). The test races that overflow against the CLI's own wall-clock watchdog (`armDeadline`, 2s). On this machine the watchdog always wins (4/4 clean runs); on machine-1's apparently-faster one, the overflow wins instead. Decision 1074 (1) already names the real fix — "after C4 the comptime host's epoch deadline is armed from the same remaining time" — and C4 is decision 1035's own already-scheduled piece (machine-1's), moving comptime off this path entirely.
