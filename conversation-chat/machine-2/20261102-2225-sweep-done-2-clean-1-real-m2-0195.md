Swept all five shapes (diagnostic only, all reverted, nothing committed). Results:

**Clean — matches commonJS exactly, no changes needed:**
- Nested generic chain (`callIt<T> → outerShow<T> → innerShow<T> → shown<T>`): `<5>`, `<hi>`.
- Recursion (`Node<T>(value, next: ?Node<T>)`, `display()` calling itself through `.next`): `1 -> 2`.

**Real bug found — needs a decision before I land anything:**
- `shown<T>` given a record or array value (`Box<T>` holding another `Box`, or `Box<T[]>`/`for`-loop over `T[]`) TRAPS at runtime (`gcUnkScalarPrint`'s fallback is a bare `unreachable` for anything that isn't a scalar/string — I never swept this when I built it). Confirmed with `GCTRACE`.
- Tried the obvious fix: route a generic-param print through the full `gcUnkPrint` (same as a real `unknown` value) instead of the narrow helper. This DOES fix both traps, correct output (`Box(Box(1))`, `Box([1, 2, 3])`, etc.) — but it reintroduces `.linear` fallback (snapshot moves, not wrong output) on 4 of the SAME modules my shown<T> landing just fixed into staying `.gc`, for unrelated gaps `__print_tagged_raw`'s walk hits in THEIR OTHER declared types (`arr_at`, `a tuple element of no known type`, `a generic field of no GC shape`, etc.) — the exact systemic fragility that made me build the narrow helper today in the first place.
- So the real fix isn't "use gcUnkPrint instead" — it's that `gcTaggedPrinter`'s walk aborts the WHOLE module on ANY one declared type's gap, instead of degrading just that one type's case (ref.test → unreachable for that type alone, every other type still dispatches). That's a change to `gcTaggedPrinter`'s own error handling, not a one-liner — flagging it rather than building it.
- Options as I see them: (a) ship the gcUnkPrint merge anyway, accept the 4 snapshot moves (same correctness, just `.linear` for those modules); (b) make `gcTaggedPrinter` degrade per-type (bigger, right fix, not scoped yet); (c) leave a record/array held by a generic param refusing (not trapping) — wrap it in the same static trap-tracking Box<T>'s OLD refusal used, so it's located instead of silent, cheapest, but short of "prints the commonJS answer" for this one shape.

**Unrelated — a separate, pre-existing defect, not B-207's:**

Confirmed this is NOT generic-specific and NOT caused by the guard: a plain non-generic enum (`Status.Ok` / `Status.Bad(code)`, its own `display()`) hits the exact same bug on the CURRENT, unmodified, already-landed compiler — `gcDeclPrinter`'s display-dispatch block only runs when `variant == null`, so a custom `display()` is never even looked at for an enum/variant value in GC mode, guard or no guard. Filing this as its own row, not touching it here.
