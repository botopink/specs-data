Checked: this is independent of 1096/B-203, confirmed — their content has no io.fs, no candidate.bp involvement, nothing in conformance/lib names i64 or bigint at all.

Both 985 and 900 now show the identical "the wasm backend would narrow this `i64` value to an `i32` slot it does not fit — in another module's code this line reaches", unlocated (`0:0`). Neither cell's own source (checked both — just `Dict<string, i32/f64>` with `mapValues`/`fold`/`insert`/`delete`/`display`, no i64 anywhere written) uses i64 directly, so it's coming from somewhere inside `std/collections`'s `Dict` itself — almost certainly its internal hash (content hashes are i64 per `hash.contentHash`). Read `wat.zig`'s two call sites for this message (31094, 31137, `lowerCoerced`/an adjacent coercion check): in `.linear` mode, a generic/`unknown` slot is a plain i32 word with no boxing path for an i64 — GC mode has `box_i64` for exactly this, linear mode has nothing equivalent. So: Dict's hash (i64) can't be carried through a generic method's `unknown`-typed slot once the module is forced to `.linear` for any reason (case/985/900 all fall to linear for their own separate, unrelated reasons; Dict's hash is what then can't be represented).

This refines 170 s7's documented symptom for 985 ("would narrow an f64 value to an i32 slot") — real symptom is i64, from Dict's hash, not the f64 return value s7 names; same mechanism, different specific value. Unlocated because it fires inside generic/compiler-synthesized specialization code with no source location propagated (a documentation/diagnostics gap worth its own small fix regardless).

This is genuinely substantial: either teach linear mode to box an i64 into a generic slot (mirroring GC's `box_i64`), or get Dict's hash off i64 for the linear path specifically — not a quick scaffold fix like 1096. Want me to scope and start that, or file it (as its own row, separate from 985/900's existing text) and pick something smaller from mt-0212's list while 1096 and this are both pending?
