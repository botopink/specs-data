Scoped (traced with gc_debug/GCTRACE again, reverted, no diff left). Picked up 985 first, found it's entangled with 900.

985's module only falls to `.linear` because of 900's exact gap: `print(prices)` on the Dict<string,f64> mapValues answers hits `gcDeclPrinter`'s refusal "a generic record's display" — the same refusal 900's own test trips directly. Once in `.linear`, mapValues' own f64-return-through-a-generic-slot then refuses too (the symptom 985's box names). So in this case, fixing 900 likely fixes 985 for free — the module would never leave `.gc`, where boxing already carries f64 vs i32 vs string distinctly, no narrowing issue.

More important: `gcDeclPrinter`'s refusal isn't an oversight. The comment right there says so — "A generic record's `display` is its one body, which linear memory reaches only through a call that binds its type parameters (`refuseUnboundTemplateCalls`): not printed here." Whoever wrote this intentionally deferred a generic record's own custom `display()` to the linear lowering's unbound-template-call mechanism, which is exactly where 900's clean, located refusal message comes from ("the wasm backend cannot call the generic `Dict.display` here: nothing at this call binds the type parameters its body needs bound"). That's working as designed — refusing cleanly, not silently wrong. 900 (3)/985 are asking for something past that design: make the call actually answer, not just refuse nicely, mirroring commonJS's fix (899/900-a): the call site hands the body hidden trailing shape parameters it reads off the static type, or — per 900's own text — the value carries its own type arguments' shapes from construction, for exactly the case where the caller doesn't know them statically (another module's value).

commonJS's mechanism is JS-specific (extra trailing args the body quietly drops if unused, free in JS). Wasm has no silent-arg-dropping — a function's signature is fixed. Mirroring it for real means: the compiled method gains real trailing shape parameters in its wasm signature; every call site either computes the shape from a statically-known type argument, or — when the caller only knows it's `Dict<K, V>` with K/V unbound, e.g. a value arriving already-built from elsewhere — reads the shape off something the value itself carries. That second case is the actual ask in 900's own wording ("a value of a generic type carries its type arguments' print shapes") and is a representation decision I haven't scoped yet: does the value already carry anything usable (GC mode's per-entry boxing tags, which exist per-VALUE not per-TYPE-PARAMETER — a `Dict<string, f64>` with zero entries carries no f64 tag anywhere), or does construction need to stamp the shape onto the Dict struct itself (a new field, decision 900's own B-114 lineage suggests yes)?

This is the fork: (a) do 900/985 together, scoping how a generic record stamps and carries its own type-argument shapes at construction (bigger, but likely the complete, designed answer, and gets both cells); (b) do 985 alone first, some narrower patch that avoids falling to `.linear` for just this shape of call (if one exists) without touching the shape-carrying mechanism — I haven't found one and doubt it exists given they share the same trigger; (c) something else. Given they're entangled in this test, I lean (a), but wanted to flag before going further — same bar as today's others.
