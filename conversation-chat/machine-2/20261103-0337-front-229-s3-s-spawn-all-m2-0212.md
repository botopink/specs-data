s3's region box is done (try/catch region in GC form, landed next with this report's queue). Before touching gcSpawnAllAnswers I measured the realistic path and found it never reaches that check.

spawnAll<T> itself is not pub — the only way in is std's runAll<T>(tasks: array<fn() -> Async<T>>) { return await spawnAll(tasks); }. Calling async.runAll([{ -> doubled(1) }, { -> doubled(2) }]) with a concrete scalar-returning doubled falls to linear with "an awaited task of a type parameter" — traced (GCTRACE) to gcAwaitedRead, called from the local-decl type inference on `val results = await …`, well before the spawnAll call itself is lowered (where gcSpawnAllAnswers's own check lives). The cause: bindAwaitedGeneric only substitutes a generic T when a parameter's declared type IS the bare name T (`p.typeRef != .named` skip); runAll's own param is `array<fn() -> Async<T>>` — T nested inside, so no substitution happens, and this is runAll's OWN generic body being type-erased, not something the caller's concrete type can fix from outside.

race<T>(tasks: array<Async<T>>) has the same T-nested-in-array shape and also falls to linear today, though on a different gap ("convert ref") — so this looks like a pre-existing, pervasive limit on every one of async.bp's generic task-array combinators, not something specific to spawnAll.

So lifting gcSpawnAllAnswers's scalar refusal alone would change nothing observable — the module still falls to linear one step earlier, inside runAll's own body. Closing s3's box for real needs bindAwaitedGeneric (or something upstream of it) to resolve a generic parameter nested inside a declared parameter's type, not just a bare one. That's a generic-inference change in the same area as front 229 s4 (machine-1's, generic-slot element classes, opus-tier) — not what gcSpawnAllAnswers's own one-line description suggested.

Options I see: (1) I take the nested-generic-param fix here too, sonnet, since the row already assigns s3 sonnet and the fix (walk the param's type looking for T, mirroring what arrayElemRef/taskValueTypeRef already do in gcSpawnAllAnswers itself) is mechanical once named, not a new design; (2) fold it into s4 instead, since it is in substance the same class of problem machine-1 is already opus-tier on; (3) I file it as its own B-row and move on to s3's third box ($box_bytes) now, leaving spawn_all's box open until s4 or the new row lands.

Recommendation: (1) — the fix is narrow (one function, mirror an existing pattern) and sonnet-appropriate per the row's own assignment; I'll hold if you'd rather it go through s4.
