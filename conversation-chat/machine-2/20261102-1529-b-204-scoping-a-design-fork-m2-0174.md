Scoped it. Found the actual shape of the gap, and it's bigger than "add a box helper" — there's a prerequisite representation gap underneath.

GC mode already distinguishes a scalar's own type from "a generic/unknown slot" as two different `Repr` values: `Repr.i64` vs `Repr{.ref = .unknown}` (both exist as live, distinct tags). `emitConvert` special-cases the pair in `.gc` mode (lines ~31086-87): scalar → unknown boxes (`gcBox`), unknown → scalar unboxes (`gcUnbox`), keyed off `to == .ref and to.ref == .unknown`.

Linear mode has no such distinction to key off. `reprOf` (line 7116): `if (self.mode != .gc or w != .i32) return w;` — for *any* linear-mode type, including a generic parameter or `unknown`, it just returns the plain scalar word (`watType`'s `.i32`) and never calls `gcReprOfType` (the function that would answer `.{ .ref = .unknown }`). So by the time a value reaches `lowerCoerced`/`lossyConversion`, a true `i32` and a generic "unknown" slot are both the exact same `Repr.i32` — structurally indistinguishable. That's why `lossyConversion(from, to)` can't special-case "boxing into an unknown slot" the way GC does: in linear mode, there's nothing to tell it apart from a real narrowing bug (`val x: i32 = someI64`), which correctly stays refused.

The fork: making linear mode track this distinction means widening what `reprOf` answers for a generic-parameter/`unknown` type when `self.mode == .linear` — today that path is never exercised (nothing in linear mode has ever produced a non-scalar `Repr` for this case), so I don't have a sense yet of how many other call sites assume "a linear-mode `Repr` is never `.ref`" and would need auditing once that's no longer true. Three ways I see to go:

(a) Do it as scoped — widen `reprOf` for linear mode's generic/unknown case to answer `.{ .ref = .unknown }` too (word-sized, same `i32` wasm slot, but a distinguishable `Repr` tag), teach `lowerCoerced`/`emitConvert` to box (`$__box_i64`/`$__box_f64`, the heap cell already used for `?i64`/a `@Result` payload) going in and unbox coming out, mirroring `.gc`'s pair exactly — then audit what else reads a linear `Repr` and currently assumes it's never `.ref`.

(b) Narrower: only widen `reprOf`'s answer along the specific call paths that reach a generic method's own parameter/return type (not every linear-mode type resolution), to shrink the blast radius — at the cost of two slightly different rules for "is this an unknown slot" depending on path, which is the kind of inconsistency 518 (4)-style rules get written to prevent later.

(c) Something else I haven't found.

This is the fork — not sure it's one a decision already answers, so flagging rather than picking (a) and running. My own read leans (a) (matches "box generically" as given, and two rules for the same question is exactly what tends to bite later), but I haven't audited enough of the file's other `Repr`-reading call sites to know how big that audit actually is before committing to it.
