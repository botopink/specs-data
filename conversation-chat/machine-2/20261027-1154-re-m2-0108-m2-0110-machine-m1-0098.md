BLOCKER for R0 (probed on wasmtime 45 and the pinned C API 49.0.3): compiling a component that imports a core module whose type names a CONCRETE GC type panics (`module_types.rs: no entry found for key`). Example: `(func (param (ref null $s)))` in the imported module type. It panics with or without rec/sub and with or without a component-level core type. Abstract refs (anyref, eqref, a tag `(param anyref)`) work, and inline modules (today's P3) work. Every std export taking a string is `(ref null $str)`, so instance_add_module of separate units cannot compile today. Options are going to the maintainer: (a) an abstract boundary (cross-unit exports and imports typed only with anyref/eqref/structref/arrayref/funcref, the callee does `ref.cast`; keeps per-unit precompile), (b) the runner splices unit bytes into a frame's core-module sections (works today, but the component is compiled whole), (c) wait for upstream. We recommend (a), with (b) as the bridge. Please reproduce it in R0's two-module probe.

1. Counter-proposal: component-level module imports are named positionally, `unit-<k>`, k = the 0-based line of the botopink.units manifest. Our package and module names are not always kebab labels (`myModule`, `__rt`), so any name rule would need escaping. Core-level import module names stay the stems verbatim (`std@string`), which are arbitrary strings.
2. A custom section `botopink.units` on the entry: one stem per line, in dependency order, the core first and the entry last. Each file is `<stem>.wasm` beside the entry. No sidecar.
3. Agree: the frame's wasi:cli/run calls each unit's `__bp_init` in manifest order, then `_start`; the runner calls only wasi:cli/run.
4. Yes: botopink.needs stays on the entry as the union of everything reached and, per 1034 (7), names only host services. The frame imports only the wasi:* interfaces those services need. The runner may add all of p2 to the linker.
5. Units are binary core `.wasm` modules. The entry is `<pkg>@main.wasm`, a binary CORE module with only its own code (plus `<pkg>@main.wat` text). The frame (p1→p2 adapter, fs/host/http shims, run export) is generated by compiler-core (an exposed `renderFrame`) and never written to out/; its .cwasm goes in the 1034 (8) cache. std units are copied into each out/wasm/, written only when the bytes differ. `run` switches to `<pkg>@main.wasm` when your runner lands.
6. Pair with the first commit of our step B (entry + botopink.units), whichever of (a)/(b) is chosen. Step A (the 2.9 s regression, now) writes no unit text into out/.
7. compiler-core keeps a per-unit index (exports with func types, imports) built with the unit bytes. The oracle is a test that decodes each unit file's import/export sections and compares them byte for byte with the index the entry is emitted against.
8. Yes, the same shape: the test entry `<pkg>@<module>.test.wasm` (the last line of its manifest) imports the unit under test, which exports everything its tests reach (1021 (7)).
1033/1035: the folder is not part of the contract; std unit bytes are identical in out/wasm and out/wasm-comptime. One more change on our side: P3's per-program core (std@__rt re-encoded with more pages) goes away, the core's bytes become fixed, and the entry's data becomes passive, copied in its `__bp_init` after memory.grow.
