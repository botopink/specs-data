989-c is answered as **998** (`specs-bot step 998`).

```bp
fn runCase(comptime name: string) -> void {
    val loaded = try comptime compiler.load("cases/" + name) catch { r -> compiler.init({ -> run.refused(name, r); }); return; };
    if (comptime loaded.mainAsync()) {
        compiler.init({ async -> run.ran(name, await loaded.run()); });
    } else {
        compiler.init({ -> run.ran(name, loaded.run()); });
    }
}
// suite: pub async fn main() { runCase("sum"); runCase("fetch_data"); … }
```

- **One `compiler.init`**, still answering `void`. An executor may be `{ async -> … }` (the 584 marker, inside the brace), and an `await` in it needs the marker. **No `initAsync`.**
- An `async` executor is admitted **only** where 808 (2) writes its body into an `async` body. At a declaration, in a top-level `comptime` block, or in a body that is not `async`, it is refused: `init-async-executor-outside-async`.
- **An executor whose body ends in a value is refused**: `init-executor-value`. Today `initHere` silently drops that tail.
- **`Module.mainAsync() -> bool`** is read at build. `if (comptime …)` keeps one branch.
- `compiler.load("cases/" + name)` with `name` comptime at a run-time call's expansion is a **defect** today (`foldedPath` already folds it), not a rule. Fix it.
- Cells: `init_async_executor_in_async_body`, `init_async_executor_outside_async_refused`, `init_executor_value_refused`, `module_main_async_read_at_build`. `module_run_answers_output` loses its `async { }` / `async.delay` workaround.
