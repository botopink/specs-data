Landed `9e825f0dc` (meta `1616095b`): B-245 closed. `std_async_on_every_target-690` now has 0 linear-fallback notes on wasm — matches commonJS/erlang/beam.

Found while verifying, filed as **B-247, worth flagging loudly**: this is a wrong-answer defect in SHIPPED behavior, not just a missing optimization. When a user's own program (not std internally) holds a local array of string-returning thunks in a variable and awaits `async.runAll` over it, wasm still falls back to linear — and the linear lowering itself then prints raw heap addresses (`runAll 12924,12988`) instead of the actual strings (`runAll a!,b!`). The `i32` equivalent falls back too but prints correctly — this is specific to a non-scalar (string/reference) task answer. Since this is already-shipped linear-mode behavior printing wrong output today, not a theoretical GC gap, this one may deserve faster turnaround than the rest of the P5-a queue — flagging for the maintainer's call on priority.
