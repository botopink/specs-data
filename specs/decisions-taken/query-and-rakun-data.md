# query-and-rakun-data — `query`'s grammar, the database context, repositories

**One grammar, two targets, picked by the source; a database query is written on the context, `from User` names a type; a repository is a `behavior` annotated `#[repository]`; parameters are typed values.**

erika is the repository `query` (`botopink/query`), outside the rakun workspace and depending on nothing of rakun (724). An `array<T>` source (`T[]`, 641) runs in memory (`` query @`…` ``, the fluent pipeline); a database query runs on `query`'s `QueryContext`, getting SQL text and typed bound parameters — `query` names no library; `from User` names a type, imported in the module and resolved at the call site (`compiler.lookup`), its table and columns its `QueryTable` meta, read at build; a `${…}` hole is a bound value, never text; an answer `?T` requires `limit 1`, a `T[]` refuses it; the grammar has `limit`, `join` and the aggregates (312). `query` declares the behavior `QueryContext<E>` — `runMany<T>(self, sql, params: QueryParam[], decode) -> Result<T[], E>`, `runOne<T>(…) -> Result<?T, E>` — and the meta `QueryTable(name, columns: QueryColumn[])`; a persistence library implements the first and records the second (397 (1), 427 (1)). In a method body the query is a template method on the context — `` return self.db.query @`select * from User where active = true`; `` —, `query` found by a name in the call site's scope (397 (3), 685); the body is assembled wholly at build: `compiler.lookup(q, "User")` answers the call site's declaration as a read-only handle, its `QueryTable` meta read at build, a type with no `QueryTable` an error at the query ("`User` is not an entity — annotate it with `#[entity(…)]`"), a field `User` lacks an error at the field; the SQL rendered at build over `runOne` / `runMany`, so the program holds the SQL as a constant and computes only the holes (415, 397 (2)). The call's type is the built code's — `Result<?User, StoreError>` under `limit 1`, `Result<User[], StoreError>` otherwise — unified with the expected type, the mismatch carrying `note: query answers a list — add limit 1 for ?User` (426). Each bound parameter is a typed value, `query`'s `QueryParam { Int(i64), Float(f64), Text(string), Bool(bool), Bytes(bytes), Null }`, built by the template from the type of the column its hole meets (`where id = ${id}` with `User.id: i32` builds `QueryParam.Int(id)`, a `?T` field `x == null ? QueryParam.Null : …`, a hole after `limit` `Int`); a hole of another type is an error at the hole at build; a value reaches the driver with its type (427). The aggregates keep the strict reading: `count(*)`; `min(f)` / `max(f)` answer `?F`; an aggregate without `group by` answers one value and refuses `order by` / `limit`; `count(f)` on a `?T` field counts the non-null rows, refused on a non-optional field; `sum(f)` answers `i64` over an integer field, `f64` over an `f64`, `0` for no rows (`coalesce`); `avg(f)` answers `?f64` (428). `dbcontext`, botopink's JPA — no longer a repository of its own but part of the workspace package `rakun-data` (dbcontext + rakun-data, 724 amending 398) — depends on `query` and std: `#[entity(name)]` / `#[column(name)]` recording `QueryTable`, `DbContext` over a `Driver` behavior, `#[repository]` on a `behavior`, `` #[query @`…`] `` and `#[nativeQuery(…)]`, the row decoding by column name; `rakun-data` keeps the drivers, the container registration, `#[transactional]`, the `/actuator/sql` inventory (398). A repository: `#[repository] behavior Users { #[query @`select * from User where id = ${id} limit 1`] fn find(self: Self, id: i32) -> Result<?User, StoreError>; }` — `#[query]` checks the query against the entity at build and records its SQL and parameters as typed meta of the method, checked against the declared answer; `#[nativeQuery("…")]` takes the driver's SQL as a comptime literal, its `:name` placeholders matched by name against the parameters, its leading keyword checked, the rows decoded by column name; `#[repository]` reads each method's meta (697) and generates `Users.Sql(ctx)`, `Users.of(ctx)` and the by-type registration; a method with neither annotation is an error; every method answers `Result<T, StoreError>` (313, 304). The statement inventory (`/actuator/sql`) is read from the `#[query]` / `#[nativeQuery]` meta (313; its `@TypeInfo.all` read is 665's registry). Template-built code is located by its expansion; `query`'s `query.bp` drops its padding when 429 lands (429). A template function is an annotation only when its signature declares the annotated declaration as its second parameter (`syntax q: string`, then `syntax decl: unknown`); called as `` f @`…` `` it is `template-annotation-only`, and a template without that parameter written as an annotation is `template-annotation-without-decl` — `rakun-data`'s `#[query …]` and `query`'s template method are two functions (696). A document repository is `rakun-data`'s `#[documentRepository]` on a `behavior` whose methods carry `` #[documentQuery @`…`] `` — a template annotation (696) whose `${name}` holes are bound to the method's parameters by `compiler.lookup` (577 (5), 802), a bound value never text, an unmatched name an error at the annotation, the text otherwise handed to the store verbatim as `#[nativeQuery]` hands SQL; the generator makes `Posts.Document(store)`, `Posts.of(store)` and the by-type registration, a method with no annotation an error, every method answering `Result<T, StoreError>` (933). Over an array `query`'s one public spelling is the grammar and std's `filter` / `map` / `flatMap` / `unique` the other; `Query<T>`'s LINQ-named methods and `of` are the template's private lowering targets, no fluent operator public (914).
