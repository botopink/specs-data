# equality — `==` is structural, user code never runs

**`==` is structural on every target, a type cannot define its own equality, `f64` under `==` is a total order.**

Records, tuples, lists and enum variants compare by value, recursively; two values of different types are never equal; erlang / beam one term, `=:=`; commonJS and wasm lower by the operands' static type — a primitive keeps its instruction, a composite calls an equality function generated per type that answers `true` at once for the same reference and otherwise compares fields in order, stopping at the first difference; no hash at construction, no interning; `!=` is the negation (210, 348). A type cannot define its own equality: `==` never calls user code, a method named `equals` has no special role, another sameness is a method with its own name (`sameAddress`); there is no `===` and no `behavior Eq`; `asserts.deepEquals` is a test helper equal in meaning to `==` (211, 348). `f64` under `==` is a total order (Java's `Double.compare`): `0.0 == -0.0` is `false` and `NaN == NaN` is `true`, bare or inside a record, tuple, list or variant, on every target; `<`, `>`, `<=`, `>=` keep IEEE ordering (214). `==` / `!=` between an `f64` and an integer literal is a compile error at the literal: `write 2.0` (215). `==` on `Decimal` compares the numeric value (`1.0 == 1.00`) (332 (3)). At build the comparison is iterative, whatever the depth (471); on wasm `$__unk_eq` is structural — one equality for every value, `#(1, "x") == #(1, "x")` answers as elsewhere (569, 738). `==` on declaration handles keeps no meaning; `compiler.same(a, b)` compares them (666).
