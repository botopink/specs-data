# library-split — which library owns what

**The shared libraries are repositories and ordinary dependencies; the compiler embeds and ships std alone; a bundled library only when justified, what is generic goes to std, and std knows no library.**

`actions`, `http`, `log`, `routing` and `validation` left the compiler for repositories of their own (`botopink/<pkg>` at `repository/<pkg>`, history kept), `cardume` joined the same way, and a program that imports one declares it in `dependencies` (326, 242, 657); a new shared package is born as a repository under the same rule (326). `snap` is the snapshot engine (391); `json`, `yaml` and `markdown` the data-format libraries, std knowing nothing of JSON (396); `query` (erika, a repository of its own) the typed-query DSL and `dbcontext` the persistence over it, now inside rakun's `rakun-data` package (312, 398, 724); `css` (a repository), `styled` (rakun's `rakun-style`) and emilia (rakun's `rakun-stylesheet`) the three CSS layers (338, 724); `cli` a library over std's CLI host primitives (506); rakun one repository, a botopink workspace of plug-and-play packages under `modules/` that joined rakun, emilia, styled, jhonstart, onze and dbcontext — each package depending on lower layers only, one version, one gate; adding a package to `botopink.json` is all a program does, its modules registering through their decorators' `compiler.init` executors — while `css`, `actions`, `routing`, `validation`, `snap`, `markdown`, `http`, `log`, `json`, `yaml` and `query` stay external (724). Each is one concern (113): `query`, `css`, `rakun-style`, `log`, `http`, `markdown` name no framework; std names no library — no table of library names in core (113, 407, 527 (5), 338 (4)). The maintainer's exceptions to 115 (two or more consumers), stated: `markdown` (one consumer, 396 (4)), `dbcontext` (one consumer, 398 (3); since 724 a part of rakun's `rakun-data`). "Two or more libraries" stays the only test: a duplicate inside one library goes to std when generic (170), else to that library's core — rakun's cookie readers were 196's case, not a package of their own (932). A bundled package may not export a name std or a framework already exports (`cookie.parse`, never `cookies`) (163) — a standing rule, 170's alias serving a program's own collisions and never the ecosystem's naming (946). std takes the natural name and a library's copy goes (`clock.parseDuration`, `async.RetryPolicy`) (170). `import {testing.snapshots} from "std"` keeps the plain unknown-module error; the pointer to `snap` is documentation (407). The `botopink/conformance` repository is deleted (467). `log` owns the sinks; rakun and `rakun-ssr` only integrate (349). The nine snapshot maps of 1.0.10 are closed (390 — § snap). A library ships `.bp` files only — no `.erl` / `.mjs` sidecar; target-native code is an inline cell in the `.bp` file (117 (8), 575 (6)). An example that combines packages lives in `rakun-ssr`; each package's examples and tests use that package alone, with no dev-dependency on another (114 (6), 113). The seven example projects 1.0.10 listed and never built are retired; every directory of `rakun/examples/` carries a `README.md` naming what it shows and the packages it uses, and a new example is born only with its gate cell (390 (5); 935). The OTP release renderers are one package of the `rakun` workspace, `rakun-release`, depending on nothing of rakun, imported by `rakun-cli` and `rakun-ssr`; 326's `release` repository is not born (917).
