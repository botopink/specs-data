# decorator-outputs-and-meta — members, associated types and typed meta

**A decorator produces typed meta, a typed member and an associated type — each under the type's path, never a free module-level name, never source text — and a name resolves where it was written.**

(1) **The places.** A decorator writes only under a type's path: a member (`Account.validate`), an associated type (`City.Columns`), typed meta; never a free module-level name, no `@emit` (216, 373, 575 (3)). The outputs are `compiler`'s, a decorator's only (`compiler-output-outside-decorator`): `setMeta<M>(syntax value: M)` (one per `M` per declaration, a second `decorator-meta-twice`), `addMeta<M>(syntax value: M)` (appends what repeats; one type is set or added, never both), `addMember<F>(name, syntax member: F)` — the typed form, the only one; the string form is gone —, `addType(name, syntax source: anytype)` — written code; the typed `compiler.addType(name, compiler.buildType(…))` replaces the string `addType(name, source)` (298, 418, 575 (3), 576 (9), (14), 578 (3), 640 (2)). A decorator adds a `pub` member (887) and never merges or replaces: a second `addMember` of one name on one declaration is `decorator-member-duplicate` at the second annotation; several annotations reach one member through typed meta (216, 404). `compiler-output-outside-decorator` does not reach a built type's members: a build body may build a type and give it members, `addMember(M, name, member)` with the target first (644).

(2) **Typed meta.** `compiler.setMeta(Entity(table: "cities"))` stores one value per type per declaration, `addMeta(Index(…))` appends; read `compiler.typeInfo(City).meta(Entity)` → `?Entity`, `.metaAll(Index)` → `Index[]`, `compiler.meta(d, M)` → `?M` / `compiler.metaAll(d, M)` → `M[]` on a handle, the type an argument (727, 840); the key is the record's type, not the decorator's name: a renamed decorator changes no reader, two decorators may write one type, one decorator several, and who may read is who sees the type (298, 576 (11)). `meta(T)` over several values is `typeinfo-meta-several`, read with `metaAll`; `metaAll(T)` answers a set-once value as a one-element array (418). The string meta is gone: `setMeta(key, value)` and `.meta.<decorator>.<key>` removed; one spelling (576 (11)). A meta record's field that holds code is written `T` and holds a tree when filled from a `syntax` (576 (12), 370 (1) as carried). A meta field holding code (written `T`, filled from a `syntax`) read in another module resolves its names where the annotation wrote them — bound under an alias no source can spell, a private one travelling as a template's private does; a same-named function of the reader is never captured (385). A generic meta record is read through `compiler.typeInfo(X).metaAll(Check)` (420, 698). A field's decorator records no meta; string meta on a method stays refused (697). **When meta is read.** A block's meta is filled after its decorators ran; a read needed before them is the located `dependency loop` (592 (5), (6), 728). Inside a decorator `compiler.meta(decl, T)` on its own handle is refused: a declaration's meta is read by the code that consumes it, after every annotation ran — a run-time body under `comptime`, a template body, or the decorator's own `compiler.init` executor, folded after every annotation of the declaration ran; annotations never depend on their order (680, 728).

(3) **Members.** A member a library's decorator writes resolves each name where it was written: the library's names in the decorator's module, the annotation's arguments in the annotated module — 112's hygiene for members; the user imports nothing beyond the decorator; `decorator-member-fn-imported-name` goes (384, 669). A typed member reads its own type's typed meta through the decorator's type parameter, checked twice — pre-comptime in the decorator's body (`compiler.typeInfo(T).metaAll(Check)` typed `Check<T>[]`), post-comptime in the annotated type; the read is a resource of build, written under `comptime` in a run-time member; no `typeInfo(Self)`: the decorator's `T` names the annotated type (395). Inside a member the owner is `decl` (626 (1)); a `compiler.*` call inside a member — `compiler.addMember("label", fn() -> string { return compiler.name(decl); })` — is evaluated at build and spliced (`"Users"`); `compiler.name(x)` with `x` the member's parameter answers `"x"` at build; `decorator-member-captures` is gone (642, 716 (3); replaces 413); a body local whose value is no literal read inside an added member or an executor is `decorator-member-local-not-literal`, located at the read (759, 575 (4)). A `behavior` takes a static member through `addMember` as a type does, and inside an added member `decl` names the owner in a type position too — `fn() -> decl` (627). Code a decorator writes resolves in the decorator's module, a type it builds included — `Field("clock", Clock)` names that module's `Clock` whether or not the annotated module imports it; what the user writes in the annotation resolves in the annotation's module; reaching the caller's scope by name is `compiler.lookup` alone (669). A decorator hands a parameter's code on only through the typed channels — typed meta or a typed member — never source text spliced into a string output (370, 281). No code identifier passes as a string: a function, a type, a field, an enum variant, an event, a hook or an action is referred to by the thing itself — a function value, a `type`, a `compiler.Field<T>` / `.name`, a variant — checked where it is written; a name that belongs to another system stays a string — an SQL table or column, a URL or route pattern, a cache name, an Erlang function, a config path, a wire spelling, text for a user (281).

(4) **Associated types.** `addType("Columns", type(id: string))` — written code (640 (2)); a type declared in the body of a type is that type's associated type (330 (7)); `City.Columns`, `Mailer.Mock` reach every importer (216). A generated type is a template text `` @`…` `` answering a type handed to `addType` (605 (2)).
