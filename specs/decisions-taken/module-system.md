# module-system — files, modules, imports and the build layer

**A file is a module, the build has a layer of its own, and an import names where its names come from.**

(1) Every `.bp` under `src/` is a module of the package, its path its name (`pages.home`, `comptime.route`); no `lib.bp`, no `mod` / `pub mod` (592 (1)). `src/main.bp` is an executable's entry (`pub fn main()`), imported by no module; a library has none (592 (2)); the manifest's `"entry"` is an executable's alone — `main.bp` when absent — and says only where execution starts, never narrowing what the package holds (677); a library has no entry, and the key in a manifest with no `main` is refused, `manifest-entry-in-library`, located at the key (733, 592 (2)). `src/comptime/` is the build layer: analysed before every other module, it imports only std, dependencies and `src/comptime/` itself, and a decorator or a template is declared only there, in std or in a dependency — else refused, located (592 (3)). `src/internal/` is private to its package; every other `pub` item is the package's API (592 (8)). The prelude of a package is any marked `pub` item outside `internal/` (592 (9), 589). `botopink.json`'s `files` is gone: what a consumer may import is the tree; once B-69 / B-75 land a manifest still writing `files` is refused, located, naming `src/internal/` (703). std's generated `unicode_tables.bp` is the flat private sibling as landed until B-75, then `src/internal/unicode_tables.bp`; a consumer's import of std's `internal/` is refused, located (913).

(2) **Every module is in the program.** Every module under the root's `src/` is checked, compiled and linked, imported or not, and its `compiler.init` executors run in 580's order (677); every module of every declared dependency joins the build the same way — `import` brings names into scope and nothing else; being declared is what makes a package's registrations run (660). The init list is ordered by dependency resolution: a package after every package it depends on, by the deepest chain, two packages of one level in the depth-first order the manifests give; inside a package, 580's order (660, 676 (1), (2)).

(3) **Blocks and order.** Modules importing each other form a block (a strongly connected component); a block's headers (`fn` signatures, types, annotated `val`s) are registered before its bodies; at run time a module-level `val` is a ref, a memoised getter (commonJS hoists its functions onto `exports` before any `require`) (592 (4)); a module's body — its `val`s, `var`s and `_` statements — runs once, in declaration order, when the module loads and before `main`, an imported module's before its importer's, dependencies first, and a `pub val` of any type is imported and read like a `pub fn` (140, 580, 660). Per block: headers, bodies, then every decorator over them, then every meta of the block is filled (592 (5), 728). The only order refusal is `dependency loop`, located: a value needing itself across modules, or a `comptime` needing a meta or a value of its own block before its decorators ran (592 (6)). Until B-72 analyses every body of a block before its decorators, a `comptime` reaching a function declared after it whose body holds a template call is refused at the `comptime`, naming the call and the remedy (702).

(4) **Imports.** `import {…} from "<name>"` resolves only to a package — std, a bundled package or a declared dependency; a module of the importing package is imported by its path in braces, with no `from` (`import {log.logger};`, `import {a.b.c as d};`); `from "<a module of this package>"` and `from "<the package's own name>"` are `error[module-import-with-from]` at the source string, the brace form the fix, std included (`import {path.relative};`) (206, 309). The brace form reaches the package's internal declarations as well as the exported ones; a package's tests are its modules too (309). A bundled package added later never changes what an import means (206). Only a direct dependency is importable: `import {rkProp} from "rakun";` with only `rakun-starter-web` declared is `error: unresolved import source "rakun" — declare it in botopink.json "dependencies"` (242). The shorthand import is gone: an item whose first segment names no module of the package and that has no `from` is `error[shorthand-import]`, its fix written (337 (1)); 337 (2)'s `mod m;` namespace binding and (3)'s `mod.bp` re-export by value are overtaken by 592 (1) — no `mod`, every `.bp` under `src/` reached by its path —, 337 keeping (1) and (4) (949); no combined form, no re-export syntax (337 (3)).

(5) **Namespaces and defaults.** `import {a.b}` and `import {a.b as X}` bind the namespace of the module `a/b`; written as a value — called, passed, bound — the namespace is the module's `pub default`, and `Card.Props`, `Card.render` reach its items; a namespace of a module with no default written as a value is refused `namespace-not-a-value`, located (582 (1)). `import {a.b.p}` binds the item, `import {a.b: {p, q}}` the items (582 (2)). A dotted path and a braced group are one tree — the dot for one leaf, the braces for several under one prefix — and only the leaf enters scope: `import {io.fs.readText}` brings `readText`, neither `io` nor `fs`; an intermediate node is a leaf when listed (`io: {fs, fs: {readText}}` brings both) (107); an imported folder module is a namespace of its submodules, so `import {io}` makes `io.fs.readText(p)` resolve (110 (2)). An imported `implement` / `extend` enters scope only when activated with `*` on its item (`collections: {ArraySets*}`), each extension opt-in by name; `*` on a namespace is refused, and `as` on a `*` leaf is `import-alias-on-activation` (107, 110 (3)). `import {pkg} from "pkg"` and `import pkg;` are one form: the package's namespace, its default the default of `src/<pkg>.bp` (582 (3)). `a.b` names either an item of `a.bp` or the module `a/b.bp`; a package holding both is refused `module-item-collision`, located at both (582 (4)). A module declares a default beside other `pub` items (582 (5)). A module's default function may be anonymous — `pub default fn (…) -> R { … }` binds no name; `pub default <name>;` makes an existing function the default; `pub default fn Name(…)` is the shorthand of both; the importer names the default (the module path's last segment, or an alias); an anonymous default's name is the module's file name (289, 213). A folder is no module and is not importable: `import {io} from "std"` is refused, located, naming the leaf `import {io.fs} from "std"` once B-69 lands, the rewrite standing until then (110 (2) amended, 919).

(6) **Aliases and same names.** An import that names its source says which declaration it means and is never `ambiguous-import-use`; two aliased imports of one name from two sources are legal, types too (`import {m1.T as A}; import {m2.T as B};`), each alias naming its own type in every position, every backend qualifying a type by its module; an un-aliased pair stays refused, `import-name-collision` (170, 310). A type of this module beside an aliased import of a same-named type is two types — identity is module + name (603); so two same-named types of two packages are two contexts too (635 points at 603). A name written between backticks is an identifier anywhere a name goes (Kotlin's escaped identifier): `` `not-found` `` — any characters but a backtick and a line break, a keyword included —, so a `.bpp` whose name is no identifier is imported `` import {pages.`not-found` as NotFound}; `` or without an alias; `` `count` `` means `count`; each backend maps the name deterministically and the diagnostic prints the backtick form; an empty `` `` `` is refused at the lexer (561). A backtick name is folded as any name into the module atom (109); two modules folding to one atom are refused on every target, the atom being every target's identity (853, 890, 831); a type application before `.` is read by the letter alone (255 (1), 854).

(7) **`import-of-failed-module`:** one error per importer at its import item — "`<name>` comes from `<module>`, which failed to check — its own errors are reported there (`<path>`)", one text for a name and a namespace; the refused module keeps its own error (545). Two files of one module path stay refused by the twin rule (`x.bp` beside `x.bpp` or `x/mod.bp`); no `.d.bp` exists (693, 575 (1)). No module-graph reflection: a declaration handle answers declarations, never a module's imports or exports; a bundler scans the text (`rakun-ssr`'s `importsOf`, failing loudly), and the module graph, when a front needs it, is a `botopink` CLI output of the resolver, a row of its own (931).

Not the rule any more: `lib.bp`, `mod` / `pub mod`, the catalogue in the root and 592 (7)'s catalogue (no catalogue is read at build; what stands of s23-i is 592 (2)'s `src/main.bp`, 729, 665), the "prefix module wins" rule and `expandImports` (592, 582); `from "std"` inside std (309); onze's (now `rakun-ssr`'s) `@/` alias (218, under § rakun-ssr).
