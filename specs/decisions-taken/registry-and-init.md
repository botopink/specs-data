# registry-and-init — `compiler.init`, the init list and the run-time registry

**A decorator registers its own declaration with `compiler.init`; the registry each marker writes is the one way to gather the declarations marked with it; no catalogue is read at build.**

(1) **The executor.** `compiler.init(syntax executor: fn())` puts the executor — run-time code compiled beside the annotated declaration — in the program's init list, to run once before `main`, at the annotated declaration's position: a module's `val`s, `var`s, `_` statements and executors in one order, source order; modules in dependency order; a declaration's `init` calls in order; any number per declaration; the hidden `val _bp_init_<k>` placed at the declaration's index (575 (3), 580, 615; `compile` was renamed `init`). Inside the executor `decl` is the annotated declaration as a run-time value, typed by the `syntax decl` parameter (581 (2), 613, 716); a `comptime` parameter and the body's `val`s enter as literals (575 (4)); a build value may be read before the executor and enter it as a literal — `val name = compiler.name(decl); compiler.init({ -> rkRegister(name, decl); })` — or read inside it, `compiler.*` there evaluated at build; both compile to the same init statement (611, 614, 642). Every module of every declared dependency and of the root is in the program, imported or not, so its executors run (660, 677); the list is ordered by dependency resolution (660, 676).

(2) **No catalogue.** `compiler.find` / `catalogue` is gone, `@TypeInfo.all` with it, `Declared<T>`, `DeclaredMeta`, `DeclaredTypedMeta` with them: nothing reads the set of marked declarations at build; a decorator registers its own declaration (`compiler.init({ -> themes.set(decl); })`) and the program reads the registry at run time; a `compiler.*` read inside the executor (`compiler.meta(decl, Entity)`) is folded at build after every annotation of the declaration ran, so it reads a settled value and a declaration's meta travels into its entry (680); a second `#[theme]` is the registering executor's refusal at init, before `main`; a type built over the whole set is not possible and nothing does it today (665, 576 (7), 353 → 665). No `comptime` default is a catalogue query: a framework's `boot` is a plain function over the registry — `pub fn boot(modules: Module[] = registry.modules()) -> App`, called `rakun.boot();` from anywhere (664, 551 → 581 (1)). The completeness refusals of the old catalogue are named `find-imported`, `find-private`, `find-hooks-reader`, `find-arguments` where their cells remain (662).

(3) **Beans and providers** (rakun's registry, built over this mechanism): constructor injection resolves a field by its type — a stereotyped type's factory is its member `T.make()`, a field `clock: Clock` resolved by the type `Clock`; no generated function name is a contract (`__rkMake_<T>` goes); a missing bean is a boot failure (234); a provider is keyed by its type and its label, never by a name string; a bean registered twice is the registering executor's refusal at init, before `main` (665, 724); a wrongly typed bean is a boot failure, narrowed with `is fn() -> T` (256, 254 as carried; the `@TypeInfo.all` half gone, 665). Two providers of one type are told apart by `#[qualifier("reports")]`, a free label recorded as typed meta `Qualifier(name: …)`; a bean is asked for with the type itself, `ctx.resolveNamed(Database, "reports")`; with no label `resolveNamed(Database)` answers the `#[primary]` provider or the only one; a constructor field takes the same marker; an unknown label, two providers of one type with one label, two `#[primary]`, or an unlabelled request among several with no `#[primary]` are errors at build (321). One way to provide a bean, `#[provides]` on a free function reading the typed config (318 (3)). Each marker registers its own declaration through `compiler.init` and the run-time registry groups by owner — `rkRoutes`, `rkBeans`, `rkHooks` and their siblings go (625 (1)). **Plug-and-play:** adding a package to `botopink.json` is all a program does — its modules register through their decorators' executors, in dependency order, with the package's defaults and the program's typed overrides (`#[rakun.config]`); `rakun.boot()` is a plain run-time function over the registry (724, 660, 664).

Not the rule any more: `@TypeInfo.all(with: …)`, `compiler.find`, a catalogue filled at an entry point (253, 235, 254, 256's mechanism, 343's catalogue read, 353, 356's `@TypeInfo.all` entry — all overtaken by 665 / 576 (7)); an expanded `boot` and `d.value` (562's example withdrawn, 581); a `comptime` default querying the catalogue (551, 664).

An executor may be `{ async -> … }`, admitted only where 808 (2) writes it into an `async` body; `compiler.init` stays one `void` function, a valued executor refused; `Module.mainAsync()` read at build lets one `runCase` serve every case (998).
