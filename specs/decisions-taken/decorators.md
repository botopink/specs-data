# decorators — a decorator is a function over the annotated declaration

**A decorator is always a function whose first parameter is `syntax decl`; its name at build is a declaration handle; each invocation is independent; a tag's annotation and a declaration's decorator are one thing.**

(1) **The form.** `#[name(…)]` names a function whose first parameter is `syntax decl`; no type or enum is an annotation by implementing a behavior — `Annotation` is gone; the data an annotation carries is a record the decorator records with `compiler.setMeta` (`pub fn mark(syntax decl: unknown, comptime label: string) -> void { compiler.setMeta(Mark(label: label)); }`, `#[mark(label: "x")]`); the enums used as keys follow: `#[stage(.Any)]`, `#[beamMemory(.Ets)]` (663). There is no `Decorator` type: a decorator's name at build is a declaration handle, two compared with `compiler.same(a, b)`; `DeclAnnotation(decorator: unknown)` (666). A marker is a decorator with an empty body, `pub fn page(syntax decl: unknown) -> void {}`; `declare fn page(syntax decl: unknown);` is refused `declare-without-implementation` (604). A decorator's other parameters are `comptime` or `syntax`; an argument may be of any type — a function, a type, a `compiler.Field<T>`, an enum, a record — checked at the argument; `.Name` resolves exactly as declared, case included, no output converting case (280 (1), (4)). A default is trailing, decorators included (244, 406). Both annotation forms are valid and printed as written: `#[a]` then `#[b]`, or `#[a, b]`; meaning identical, each item its own annotation in written order (286). A decorator reached through a namespace import runs, whatever module declares it — `#[ns.d]` is `#[d]` imported by name; an annotation is never accepted and not run (386)., a std decorator too — a leaf import annotates by the name (669, 881). No module-level annotation: `#![…]` stays a parse error, an annotation always annotates the declaration that follows (315). A name after `#[` that is no decorator is B-145's refusal (663).

(2) **The handle.** The declared type of `syntax decl` is the contract the annotated declaration must meet: `syntax decl: unknown` admits any declaration and gives `decl` no member (`decl.make` is the checker's own `unknown has no member`); `syntax decl: Module` (a behavior) admits a type that implements it — one without `implement Module` refused at the annotation, located, naming the type and the behavior —; `syntax decl: fn(…) -> R` admits a function, `decl(…)` callable; `syntax decl: T` keeps the type; the check is the written `implement` clause, the member then 800's (716 (1); 626 (2)'s structural reading superseded, 842); a member the decorator adds is never counted in `decl`'s type — `decl` has only what the annotated declaration itself declares, so a decorator never calls on `decl` a member it adds (797). A member it needs is held as a value — written once, added, and handed to its executor and its other members (842). Inside every tree the decorator writes — an `init` executor, an `addMember` member, in a type position too — `decl` is the annotated declaration itself as code, bound to that declaration, never "what the name resolves to in the module": a `fn` is the function value, a `val` its value, a type the type in expression position (`decl.make()` is `Users.make()`, `decl(repo)` its constructor), a method `Users.make` by its owner's path, a behavior the behavior name, a field its owner's field; `-> decl` is the annotated type or behavior (613, 626 (1), 627, 716 (3)). The decorator's body and its trees are type-checked once, at the decorator, against the parameter's type; an annotation is checked only against the contract; no error surfaces inside an executor with a `called from` line (716 (2)). A member's handle names its owner, `compiler.owner(d)`, `null` at module level (526, 576 (3)); a method-level decorator sees its own method — name, parameters, return type, module — and the type-level decorator reads the type and every method with its annotations; a method marker is placement (347). A type's or a behavior's methods' decorators run before the owner's; a method's `setMeta` / `addMeta` is kept for its owner (one value per type and method, `decorator-meta-twice`) and the owner's body reads it through `compiler.methods(decl)` and `compiler.meta(m, Q)` (697). No `decl.loc`: `compiler.src()` in a decorator body is the annotated declaration's location (718, 575 (3)), legal, a value an output may carry — a diagnostic, a snapshot, a meta — and never a route: a route reaches `#[page]` as an argument, nothing of a file's place names a page (403, narrowed by 734). A decorator on a `val` runs over a handle of kind `Val`; `setMeta` legal, `addMember` / `addType` refused (356); a user decorator on a module `var` is refused at the annotation, `#[beamMemory(…)]` untouched (710). Inside a decorator, `compiler.meta(decl, T)` on its own handle is refused — a declaration's meta is read by the code that consumes it, after every annotation ran; a `compiler.*` read inside the decorator's `init` executor is folded after every annotation of the declaration ran, so `compiler.meta(decl, Entity)` there is allowed (680). A decorator never reads a body (655 → 576 (8)).

(3) **Independence and order.** Each invocation is independent: a decorator's answer depends on its declaration alone; a module `var` written by a decorator body stays refused (343). The order decorators run in never changes an answer (347). Provisional: a decorator that reads `compiler.hooks(d)` runs last in its module and only records meta or refuses — `addMember`, `addType` in it `decorator-hooks-output` (372, 576 (8), 725). A same-module typed meta read of its target is 592 (5)'s: the meta of a block is filled after its decorators ran, and a read needed before them is the located `dependency loop` (592 (5), (6), 728; 419 replaced). A duplicate across declarations — two `#[provides]` of one type, two handlers of one route — is the registering executor's refusal at init, before `main`, naming both (665, 343 as amended).

(4) **Errors in added code.** A type error inside code a decorator added is located at the annotation that added it, the message naming the member or associated type by its owner's path and the decorator's `addMember` / `addType` call with its file and line (567). A second `addMember("validate", …)` on one declaration is `decorator-member-duplicate` at the second annotation; several annotations reach one member through typed meta (404, 216). A decorator's per-function code is generic library code fed by meta: `#[page]` records its route in typed meta and a page reads its segments with `use params<P>()` (236).

(5) **Tags.** A tag's annotation and a declaration's decorator are one thing: on a tag, `compiler.kind(decl)` is `Element` or `Component` (`compiler.component(decl)` the component's own handle, the tag's name and static attributes readable), and the channel is typed meta — the annotation records, the template function reads it back by type; `addMember` / `addType` on a tag refused; the meta types `Hydrate`, `Defer`, `RawBody`, the transition metas, `isInline`'s style meta, `LinkReload`, `LinkHistory`, `ClassName(names: string[])`, `StyledMeta`; one `setMeta` per type per tag, `addMeta` repeats; a template function building a tag's handle and reading its meta is generic compiler surface (302, 576 (3)). A template body builds a tag's handle with `compiler.tagDecl(kind, name, syntax attrs)` and runs its annotation through `compiler.annotate(d, at: Span)`; the annotation's text is read from the span, never passed as a string (636). Outside markup, expression-level work is a call; a tag's annotation is the one expression-position decorator, `val x = #[deco] 1;` refused (705). A handle `compiler.bindings(e)` answers has no read of the decorator that annotated it; a template body tells annotations apart by the meta they recorded (679).

(6) **Where a decorator is declared:** only in `src/comptime/`, in std or in a dependency (592 (3)). No `@emit`, no `@code`, no `@expr` (605, 575 (8)): a registration is an `init` executor, a generated type a template text handed to `addType`, a generated function a typed `addMember`, a generated helper beside a `fn` a run-time helper of the library (605 (1)–(4)). `compiler.wrapWith` is gone: a decorator never changes what a call does without the caller seeing it; behaviour around a type's methods is a proxy type the decorator builds (`OrderService.Tx`), around one function a function written around the call (`retry(policy, { -> issue() })`) (714).
