# process-and-ownership — fronts, machines, threads, ordering

**Only 144 edits botopink-lang (and 164 the wasm target); a structural fix comes first and other fronts pause for it; a thread reads `thread-rules.md` first and reports in four lines.**

(1) **The cut by repository.** The milestone's specs are cut by repository in three tiers: 144 holds every open step that changes `repository/botopink-lang`, in one ordered list — first comptime on wasm (B-00), then 431 / 432 (B-01–B-09), then the structural fixes (B-10–B-19), then the rest; only 144 edits botopink-lang, and a library front that meets a compiler or std gap files a `language-gaps.md` row and pauses on the 144 step that fixes it; one front per library repository (145 query … 161 vscode-extension; the open steps of 148, 149, 153, 154 and 162 refiled under 150 rakun, 724), a package's consumer commits staying with the package's front, producer first; the medium fronts; every new README opens with an alias table from the old ids; the old track directories are deleted, an old front's goal and topic files kept beside the steps that took its work; a front keeps its number for good; at most six fronts run at once (433). rakun, emilia, styled, jhonstart, onze and dbcontext (now `rakun-stylesheet`, `rakun-style`, `rakun-bpp`, `rakun-ssr`, `rakun-data`) are one repository, `botopink/rakun`, so their fronts' open steps are refiled under 150, with lanes by layer (724, amending 433). Front 164 wasm-gc is the second front that edits botopink-lang, owning the wasm target, the comptime runtime, std-wasm, beam-to-wasm and compiler-web (544). The subtree `conformance/modules/decisions-taken/**` is front 166's, the one carve-out (651). botopink-lang's runners are 144's, the meta's `scripts/**` 163's (658). The specs are laid out by machine: `machine-1/` (the checker and the language, the libraries' lane, 165, 136, 105, 135) and `machine-2/` (`144-backends-tooling/` with `164-wasm-gc`, 163, 107, 98, 166), each folder's README that machine's work queue — what it executes without a maintainer decision, in order, every item fixed by a decision or a step's README; what waits on the maintainer is listed at the queue's end and is not opened, a thread that reaches it stopping and reporting (744). Front 164 runs on machine 2 in a `--lang` worktree of its own, ahead of every other open step of 144 that machine holds; a step reaching the wasm target, the comptime runtime or std-wasm waits on 164 s2; B-30 is closed as superseded (741). Front 166 — one cell per decision, in the repository it binds — has priority medium: the ledger becomes code, every decision in force one real program the gate checks once the gate is solid (749).

(2) **Structural fixes first.** When a front meets a cause that is structural — a defect or gap of the compiler, std or a shared layer that a library would otherwise work around — the fix opens at once as a step of its owning front, ahead of that owner's other open steps, and every front that would build on a workaround pauses on it; no new workaround is written; an existing one is removed in the fix's landing (430). A step gate's reach follows the backend partition (460, 249).

(3) **Threads.** Every thread reads `scripts/thread-rules.md` first; its prompt states only the task's own step, boxes, worktree and model; it rebases onto `origin/feat` right before its final commit; its report is four lines — Done, Commits, Outside, Questions; spec and decision text is never written on `haiku`; a thread that writes a cell's expected answer runs on `opus` unless its prompt fixes every answer; the number of threads is bounded by the pool's jobs (484). `scripts/gate.sh exec` runs one command under the pool (674); that every heavy command of a thread runs through it is `scripts/thread-rules.md`'s (the maintainer, 2026-10-12; 731 (13)). `fable` works where no oracle checks the work, with small inputs, and never implements unless a plan and its `sonnet` / `opus` build both failed: a `Plan` thread on `fable` plans a design step and `sonnet` (or `opus` for typed design) builds the pieces; a targeted review after a landing reads only the changed answers, the report's Outside and Questions and the decisions' text, answering per point (A) the language, (D) a defect with its 144 / 164 row and cell, (Q) a maintainer question; the review is a trigger, never a routine (742). At each landing, each thread's end and before each status report the coordinator reconciles the listing with what runs: a thread is active only if something of it runs; a finished thread is stopped (`TaskStop`) and its worktree removed; orphan `until … sleep` / `while … sleep` loops are killed by PID (a loop waiting on `pgrep -f <pattern>` matches itself and never ends; every prompt says kill your own background jobs before reporting); no slot stays idle — each free one takes the next work that needs no maintainer decision and touches no running thread's area, up to about five threads, the pool and memory permitting, what stays blocked named with what blocks it (743). The builtins group (575) is next on both machines in 605's order as 617 and 625 amended it — B-136 → 165 s10 → B-137's tail → B-138's boxes → B-139 → B-149 → B-148 → B-140 —; until B-140 lands no other new step opens, except an item of the queues' § After the group whose files are disjoint from the group's open threads (`libs/std/**`, the builtins, `compiler.bp`, the backends' `Implementation` readers, the `decorator_*` / `template_*` / `comptime_*` cells); the group's threads commit with `--no-verify` after their own reached checks, the one exception to `scripts/thread-rules.md`, stated in each prompt; one full gate (`scripts/gate.sh --cold` with conformance, on each machine's main checkout) runs at the group's end before B-140's landing; machine 1 holds botopink-lang's `feat` until B-136 lands and posts the hash to machine 2 (745, 746). Every report to the maintainer and every reply is a file of `repository/conversation-chat/<machine-N|all>/`, `<YYYYMMDD-HHMM>-<slug>-<id>.md`, opening with its `TEMPLATE.md`'s head (`from`, `to`, `purpose`, `subject`, `read`, `in-reply-to`), pushed to that repository's `feat` at once; the machine runs `scripts/unread.sh <side>` before writing and ticks what it read; no decision lives there (747).

(5) **The ledger.** The ledger is two files: `decisions-taken-steps.md`, the record — one numbered row per decision in the order taken, the next free number at its top, the file `decisions-split.py` and `decision-cells.py` read; append-only from 730 on, a landed row never edited, an amendment a new row —, and `decisions-taken.md`, the rules in force, one text per subject under a stable slug (never a number), each sentence citing its rows, closed by `Steps:` and `Binds:`. A decision lands as a row in the steps and as a sentence in its subject, in one commit; where the two differ the later row number wins until the subject is corrected. The repositories' generated `decisions-taken.md` keep their name and content (482); the subject file is the meta's alone (730). The four files live once, above every milestone — `specs/decisions-taken.md`, `specs/decisions-taken-steps.md`, `specs/decisions-pending.md`, `specs/decisoes-pendentes.md` —, the numbering global, so no milestone repeats or keeps a copy: the closed milestones' copies were folded into them and deleted on 2026-10-18 (748). The commit that writes a decision retiring a spelling rewrites every line of the current milestone's specs and open READMEs that writes the old form as current (a history sentence, a decision's own text, a codemod's rule and a refusal cell keep it) and adds the form's row to `specs/retired.md`, the inventory of retired forms; the duty is the writer's, measured by 141's sweep at the milestone close, with no allow-listed check in `land-check.py` (945).

(6) **The standing principle.** Where options offer refuse against accept, or fail against warn, the stricter side is the default unless it would have to invent new semantics to exist; an exemption that cannot be avoided is structural — a directory the tool knows, a form the grammar does not admit — and never a knob: no skip list, per-file pragma or environment variable, and "keep the strict behaviour and add a flag for the people it inconveniences" is no answer this record recommends (67). Every milestone carries one `status.md`, the only spec file that carries status, updated in the commit of the work it reflects (69); a closed front's spec is condensed to its outcome and its open items — status narratives, commit hashes and removed spellings leave it, a removed spelling appearing only in the record (135); when a README and its example disagree, the example changes (78).

(conf) **Conformance is machine 2's, until the maintainer says otherwise (768):** the suites' runs, the pipeline's reds (fixed or filed), the cells' reference and spelling, 166's cells in every repository, B-157. Machine 1 writes the cells its steps call for inside its landings and runs what its change reaches (458, 459, 465), opens no conformance thread, runs no suite-wide pass, and names a red it meets to machine 2 through the chat (747). Machine 1 runs everything that is not conformance and skips every Conformance step, moving to the step after it; machine 2's parked compiler items pass to machine 1 in 769's order, each parked worktree pushed as its `front/<name>` branch and named in the chat; machine 2's queue is conformance alone (769).
