# caches-and-build-outputs — where a build writes and what it may reuse

**Every cache lives under `.botopinkbuild/`, only dependencies are cached, and nothing a test exercises comes from a cache.**

(1) Every build cache lives under `<root>/.botopinkbuild/cache/` (`<root>` the workspace root, else the project root): deleting `.botopinkbuild/` deletes it all; `botopink clean` deletes it whole; `gate.sh --cold` deletes the cache of every root it reads; nothing in `$HOME` or `$XDG_CACHE_HOME` (225). The language server's cache is `.botopinkbuild/cache/lsp/` of the opened project; `~/.cache/botopink-lsp` goes (233).

(2) **One code cache, the CLI's, for every target.** The package under test — a cell's own package, the member whose tests run, the project built or run — is always analysed, generated, compiled and run; only its dependencies may come from the cache (509 (1)). Level A, first: every target's toolchain step after the codegen, for a dependency's modules, under the key of its input bytes and the tool's version (erlang `.erl` → `.beam` with the options and the OTP / erts / `compiler` / `stdlib` versions, a source with `-include` or `parse_transform` never looked up; wasm's assembly and its runtime's precompile) — one mechanism, replacing `cache/erlcheck` and `cache/beam`, read by `build`, `run`, `test` and `cell check` (509 (2)). Level B, later and only after the invariant "a package's analysis and generated code depend on its dependency closure alone" is proved by a test: a dependency's checked interface and generated code per target (509 (2)). The closure key is a hash of the package's files by content, its dependencies' closure keys (Merkle), the target and the compiler's sources by backend partition, never the binary's hash alone (509 (3)); the partition is `codegen/backend-partition.txt` — every source not assigned to one backend is shared and in every key (249). An entry is stored by hash, never by name; a program never runs from the cache — an entry is materialised (hard link, else copy) into the project's output (509 (4)). a cold run — `scripts/gate.sh --cold`, botopink itself having no `--cold` (739, 754) — reads nothing and writes what it ran; CI and a landing run cold; only a success is stored, nothing when a key cannot be computed with certainty; concurrent writers stage and rename, no lock (509 (5)). B-77 then makes `botopink cache` the one place of the build infrastructure: level A moves to `.botopinkbuild/build/` beside level B's `.botopinkbuild/analysis/`; `cell check` and `test` take their jobs from the machine's pool (468 / 473's directory and formula, moved into botopink) and report in the units' order; `--jobs` and `--cold` leave `build`, `run`, `test` and `cell check`; `botopink cache clean` / `status` are its own section of `--help`; the scripts and the libraries' runner keep only the hook's flags (`--staged`, `--no-conformance`), losing their cache logic and the pool; botopink knows cells and workspaces only, never a conformance suite, a hook or a CI (739). Every file `compiler.embed` reads joins the closure key (519, 607 (1)).

(3) **No test result is cached:** a pass is never stored nor answered from a store; the result store of `cache/results/lib-test` is removed; a gate is made fast by the code cache and by running only what a change reaches, never by skipping a run (510). compiler-core's own snapshot tests keep no runtime-output cache either; an interrupted `erl` is never recorded (922).

(4) **Units.** A module's tests are a unit of their own; its production unit is the same in `build`, `run` and `test`: every module emits its production unit always and, under `botopink test` of the package under test only, a test unit holding its `test` blocks, marked by the `__test__` prefix (erlang `'__test__@rakun-stylesheet@spacing'`, commonJS `__test__/rakun-stylesheet/spacing.js`, wasm linked only under `test`); a type's unit keeps `@@` (513 (1)). A test reaches a private function or module `val` through a reserved export the production unit always carries (`'__bp_priv__<name>'/N`, one hidden export object on commonJS, none on wasm); the runner is one, at the test entry (513 (2)). A dependency's test units are never emitted for a consumer; a test unit is never cached (513 (3)). A dependency's module set is one in every command: with no `.d.bp`, a dependency's module that does not check is refused by `build`, `run`, `test`, `check` and `cell check` alike (514, 515, 586, 575 (1)). In a project whose modules sit in folders, a module in the project's own `src` belongs to the project, never to a dependency named after its first folder; a type's compiled units are written beside the module that declares it (317).

(5) A trace's listing is lowered again from the module's Erlang text each time a snapshot or the code cache reads it; the wat build cache keeps the Erlang text, never the listing (692).

(6) **Output layout and atoms.** The erlang and beam outputs are flat, one directory per target (`out/erl/`, `out/beam/`), each file named by its module atom; commonJS and wasm keep `out/<module path>` (6, 109). A module's BEAM atom is `<package>@<path>` — the `botopink.json` `name`, then the module path with `/` as `@`, lowercase, any other character `_` — and a declaration's is `<module>@@<Decl>` with its case kept (`std@math`, `std@io@fs@@File`, `myapp@main@@SourceLocation`), one rule for a `type` and for the `val` an `implement` is bound to; the same atom is the value's identity on both BEAM targets (109, 21); a package name must start with a lowercase letter, refused at the manifest and by `botopink new`; a compilation with no `botopink.json` is refused on erlang and beam, nothing guessed from a directory; the compiler's tests compile as the package `test`, the comptime's modules as `bp`, a package named `bp` refused; two declarations of one module whose atoms differ only by case are refused (109). A `behavior` emits no module (23, 109).
